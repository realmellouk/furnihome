FurniHome Presentation Report

1. Project Overview

FurniHome is a Laravel furniture e-commerce website. It lets users browse furniture categories, view product details, choose product variants, add products to a cart, checkout, and view order history.

The problem it solves:
Customers can explore furniture online instead of visiting a physical shop first. They can compare products, see prices, choose variants, and place an order from home.

Target users:
- Normal customers looking for furniture.
- Store/admin staff who manage products and orders.

What makes it useful:
- Clean furniture-focused design.
- Product categories and collections.
- Cart and checkout system.
- Admin dashboard for products and order status.
- Delivery and installation information included in checkout.


2. Technologies Used

- Laravel 12 / PHP 8.2: backend framework, routing, controllers, validation, authentication, database models.
- MySQL / MariaDB: stores users, products, categories, carts, orders, payments, deliveries, installations.
- Blade views: frontend templates in resources/views.
- CSS/JS: active frontend uses public/css/furnihome.css, public/css/admin.css, and public/js/furnihome.js.
- Vite/Tailwind: configured in vite.config.js, resources/css/app.css, and resources/js/app.js, but the main layout currently loads the public CSS/JS files directly.
- Laravel packages: standard Laravel framework, Tinker, PHPUnit, Pint, Sail, Faker, Collision.

Important files:
- routes/web.php
- composer.json
- package.json
- vite.config.js

4. Normal User Journey

1. User visits /.
2. User browses categories and collections.
3. User filters products by category.
4. User opens a product page from /products/{product}.
5. User selects a variant and quantity.
6. If not logged in, Add to Cart and Buy Now redirect to login.
7. User registers or logs in.
8. User adds product to cart.
9. User opens /cart, updates quantity, or removes items.
10. User clicks checkout.
11. User enters name, email, phone, city, address, and delivery note.
12. User chooses free installation or no installation.
13. User chooses cash on delivery or simulated card payment.
14. System creates order, order items, payment, delivery, and installation records.
15. Cart is cleared.
16. User sees order confirmation.
17. User can view order history and invoice in /my-orders.

Important note:
No wishlist feature exists in the code.


5. Admin Journey

1. Admin logs in using admin@furnihome.com.
2. Login redirects admin to /admin/dashboard.
3. Admin sees:
- total products
- completed orders
- cancelled orders
- customers
- total sales
- latest orders
- latest products
4. Admin opens /admin/products.
5. Admin can add, edit, or delete products.
6. Product form supports category, name, price, old price, dimensions, material, description, and main image upload.
7. Admin opens /admin/orders.
8. Admin can update:
- order status
- payment status
- delivery status
- installation status

Important note:
There is no separate admin page for managing categories, users, contact messages, reviews, delivery staff, or installation staff.


6. Database Explanation

Live local database currently has:
- 8 categories
- 23 products
- 69 variants
- 3 users
- 2 orders
- 0 cart items

Main tables:

users
- Purpose: stores customers/admin accounts.
- Important columns: name, email, password, phone, role.
- Relationship: user has carts, orders, addresses, and reviews.

categories
- Purpose: stores furniture categories.
- Important columns: name, description, image.
- Relationship: category has many products.

products
- Purpose: stores furniture catalog.
- Important columns: category_id, name, description, price, old_price, material, dimensions, stock, status, main_image.
- Relationship: product belongs to category.

product_variants
- Purpose: stores product image/color variants.
- Important columns: product_id, color_name, image, stock_quantity, price.
- Relationship: variant belongs to product.

carts
- Purpose: stores one user cart.
- Important columns: user_id.
- Relationship: cart belongs to user.

cart_items
- Purpose: stores items inside cart.
- Important columns: cart_id, product_id, product_variant_id, quantity, price.
- Relationship: item belongs to cart, product, and variant.

orders
- Purpose: stores customer orders.
- Important columns: user_id, order_number, subtotal, delivery_fee, installation_fee, total, status.
- Relationship: order belongs to user.

order_items
- Purpose: stores products bought in an order.
- Important columns: order_id, product_id, variant_id, product_name, quantity, price, total.
- Relationship: item belongs to order.

payments
- Purpose: stores payment information.
- Important columns: order_id, payment_method, payment_status, amount, transaction_reference.
- Relationship: payment belongs to order.

deliveries
- Purpose: stores delivery information.
- Important columns: order_id, full_name, phone, city, address, delivery_fee, status.
- Relationship: delivery belongs to order.

installations
- Purpose: stores installation request/status.
- Important columns: order_id, is_requested, installation_fee, status.
- Relationship: installation belongs to order.

addresses
- Purpose: stores saved address structure.
- Important columns: user_id, full_name, phone, city, address_line.
- Important note: table exists, but checkout currently saves address to deliveries.

reviews
- Purpose: stores product reviews.
- Important columns: user_id, product_id, order_id, rating, comment, status.
- Important note: table exists, but no review UI is implemented.

Simple database diagram:

User
  - Cart
    - Cart Items
      - Products
      - Product Variant
  - Orders
    - Order Items
      - Products
    - Payment
    - Delivery
    - Installation

Simple explanation for teachers:
One user can have a cart and many orders. Products are organized by categories. When checkout happens, cart items become order items, and the system creates payment, delivery, and installation records.


7. Code Logic Explanation

Authentication:
- Controlled by AuthController.
- Login validates email and password.
- Register validates name, email, phone, and password confirmation.
- Passwords are hashed.
- Session is regenerated after login/register.
- Logout invalidates the session.

Admin permissions:
- Controlled by AdminMiddleware.
- Admin access is based on email admin@furnihome.com.
- The role column exists, but the actual middleware does not use role = admin.

Product management:
- Public products are loaded in HomeController.
- Product details are loaded in ProductController.
- Admin product CRUD is in AdminProductController.
- Admin image uploads go to public/images/products/admin.

Cart logic:
- Only logged-in users can access cart routes.
- CartController@store validates product, variant, and quantity.
- If the same product and same variant already exist, quantity increases.
- Otherwise, a new cart item is created.
- Users can update quantity or remove items.
- Security: users cannot update/delete another user's cart item.

Order logic:
- CheckoutController@store validates checkout form.
- It calculates subtotal, delivery fee of 50 MAD, installation fee of 0 MAD.
- It creates order, order items, payment, delivery, and installation inside a database transaction.
- Card payment is simulated: payment becomes paid and gets a random reference.
- Cash on delivery stays pending.
- After order creation, cart items are deleted.

Validations:
- Product creation validates category, name, price, dimensions, material, and image type.
- Login/register validate required fields.
- Checkout validates customer information, installation option, payment method, and required card fields if card is selected.

Security:
- Laravel CSRF tokens are used in forms.
- Passwords are hashed.
- Auth middleware protects cart, checkout, and orders.
- Admin middleware protects admin pages.
- Order pages check that the order belongs to the logged-in user.


8. Strengths

- Professional furniture design and branding.
- Complete customer shopping flow from product browsing to order confirmation.
- Product variants with image switching.
- Cart quantity update and remove actions.
- Checkout includes delivery, installation, and payment simulation.
- Admin dashboard exists.
- Admin can manage products and update order statuses.
- Database relationships are well separated.
- Good use of Laravel models and controllers.
- The site has real local product/category data.


9. Weaknesses Or Limitations

Present these professionally:

- Admin permission uses a fixed email instead of the role column. Improvement: use role = admin.
- Categories cannot be managed from admin UI. Improvement: add category CRUD.
- Contact form only shows a frontend success message; it does not save messages.
- Coupon/promo inputs are visual only; no discount logic is implemented.
- Cancel Order button appears in order history but has no backend route.
- Forgot password link appears but no reset route is implemented.
- Reviews table/model exists, but users cannot submit reviews yet.
- Address table exists, but checkout stores delivery address directly in deliveries.
- Delivery staff and installation staff columns exist, but there is no staff assignment screen.
- Automated feature test fails because the test database is missing categories; local MySQL migrations are run, but test setup needs migration/seed configuration.

12. Full Speech Script

Member 1:

Good morning teacher and classmates. Today we are presenting our Laravel project called FurniHome. FurniHome is an online furniture shopping website. The idea is simple: instead of going directly to a furniture store, the customer can browse products online, see categories, view product details, add items to the cart, and place an order.

The website is made for two types of users. The first type is the normal customer, who wants to buy furniture. The second type is the admin, who manages products and orders. FurniHome is useful because it makes furniture shopping easier, faster, and more organized.

Member 2:

Now I will explain the technologies used in the project. The backend is built with Laravel, which is a PHP framework. Laravel helps us organize routes, controllers, models, validation, authentication, and database operations.

The database is MySQL. It stores users, categories, products, carts, orders, payments, deliveries, and installation requests. For the frontend, we used Blade templates, which are Laravel view files. We also used custom CSS and JavaScript for design, animations, product filters, variant image switching, and checkout payment fields.

Member 3:

I will explain the customer journey. First, the customer visits the homepage. On the homepage, they can see the hero section, categories, collections, and product list. The customer can filter products by category, for example Living Room, Bedroom, Dining Room, Office, and Decor.

When the customer clicks a product, they go to the product details page. There they can see the product image, description, price, material, dimensions, and available variants. They can choose a variant and quantity. If they are not logged in, the website asks them to login. After login, they can add the product to the cart or buy it directly.

In the cart page, the customer can increase or decrease quantity, remove products, and continue to checkout. In checkout, they enter delivery information, choose free installation or no installation, and choose cash on delivery or simulated card payment. After placing the order, they see an order confirmation page. Later, they can open My Orders and see their order history and invoice.

Member 4:

I will explain the admin side and database. The admin logs in using the admin email and goes to the admin dashboard. The dashboard shows total products, completed orders, cancelled orders, customers, total sales, latest orders, and latest products.

The admin can manage products. They can add a new product, edit an existing product, upload an image, or delete a product. The admin can also manage orders. In the orders page, the admin can update the order status, payment status, delivery status, and installation status.

The database is organized into related tables. Users can have carts and orders. Categories contain products. Products have variants. Cart items become order items after checkout. Each order has payment, delivery, and installation information. This structure makes the project organized and easy to extend in the future.

Member 5:

I will explain the important backend logic. Authentication is handled by Laravel. Passwords are hashed, forms use CSRF protection, and private pages are protected by middleware. Cart, checkout, and order pages require login. Admin pages require the admin middleware.

The cart logic checks the selected product and variant. If the same product and variant already exist in the cart, the quantity is increased. The checkout logic calculates subtotal, delivery fee, and total. Then it creates the order, order items, payment, delivery, and installation records inside a database transaction. This is important because it keeps the order data consistent.

The strengths of FurniHome are the clean design, complete shopping flow, product variants, cart, checkout, order history, and admin management. Some future improvements are adding real payment integration, category management, contact message storage, reviews, coupon logic, and better role-based admin permissions.

To conclude, FurniHome is a functional Laravel e-commerce project for furniture shopping. It shows how frontend design, backend logic, and database relationships work together in a real website. Thank you for listening.


13. Possible Teacher Questions And Answers

Q: Why did you choose Laravel?
A: Laravel gives us routing, controllers, models, validation, authentication, and security tools. It helps us build the project faster and in an organized way.

Q: Why MySQL?
A: MySQL is good for structured data like users, products, carts, and orders. It also works well with Laravel and XAMPP.

Q: How does the cart system work?
A: Each logged-in user has a cart. Cart items store the product, selected variant, quantity, and price. If the same product and variant are added again, the quantity increases.

Q: How does checkout work?
A: Checkout validates customer information, calculates subtotal plus 50 MAD delivery fee, creates the order and related records, then clears the cart.

Q: Is the card payment real?
A: No. It is a simulation. The card fields are validated, but real payment processing is not integrated.

Q: What is the role of the admin?
A: The admin can view dashboard statistics, manage products, and update order, payment, delivery, and installation statuses.

Q: Does the project have roles?
A: The database has a role column, but the current admin access is checked using the email admin@furnihome.com. A future improvement is using the role column properly.

Q: What problems did you face?
A: Organizing the checkout flow was challenging because one checkout creates many records: order, order items, payment, delivery, and installation.

Q: How did you solve it?
A: The project uses a database transaction, so all checkout records are created together. If something fails, the database does not save incomplete order data.

Q: What future features would you add?
A: Real online payment, wishlist, product reviews, category admin management, contact messages, coupon system, order cancellation, and better role management.

16. Clean Final Summary For ChatGPT

FurniHome is a Laravel 12 furniture e-commerce website. It uses PHP/Laravel for backend logic, MySQL for the database, Blade for frontend views, and custom CSS/JavaScript for design and interactions. Customers can browse categories and collections, view products, choose variants, add products to cart, checkout with delivery and free installation, and view order history and invoices. Admin can log in, view dashboard statistics, manage products, and update order/payment/delivery/installation statuses. The database includes users, categories, products, variants, carts, cart items, orders, order items, payments, deliveries, installations, addresses, and reviews. Main strengths are clean design, complete customer shopping flow, admin management, and organized database relationships. Main limitations are no real payment gateway, no wishlist, no review UI, no saved contact messages, no coupon logic, no category admin CRUD, and admin access uses a fixed email instead of the role column.
